## 3. 逐处改动清单

### 3.1 删除：带 JS 的摇杆页 `PAGE`（基线 125~267 行，约 5.4KB）

**为什么删**：这一页的语义是"按住发帧、松手发 0"，和扩展版"点一下保持"是**两套
互斥的状态机**。留着它，手机只要开着这个页，每 100ms 就会把服务端刚设好的
`action=fwd` 用 `sp=0` 覆盖掉 —— 表现为"车走一下就停"，而且极难定位。
README 第 6 条也明确要求 `/h` 零 JS。**只留一个控制入口，状态才不会有两份。**

### 3.2 删除：静态页 `PAGE_H` / `PAGE_T`（基线 277~324、327~346 行）

**为什么**：静态 HTML 没法显示状态，也没法高亮当前按钮。改成函数 `_page_h(st)`
按状态现拼（约 3.5KB，见 `/ver` 的 `PAGE_BYTES`）。`/t` 调试页的功能被 `/h`
完全覆盖，删掉；访问 `/t` 现在回 404。

### 3.3 `/` 的行为：回 JS 页 → **302 跳 `/h`**（基线 754~771 行）

**为什么**：见 3.1。保留一个"打开就会打架"的入口没有意义。
现在 `/`、`/index.html`、空路径统一 302 到 `/h`，用户只需要记一个地址。

### 3.4 `/cmd` 重写（基线 645~706 行 → `_handle_cmd()` + `_apply_cmd()`）

| 项 | 基线 | 扩展版 |
|---|---|---|
| 参数 | `st` / `sp` / `ht` / `sq` | `m`（模式）/ `a`（动作）/ `ht` / `sp` / `ref` |
| 语义 | 一次请求 = 一帧指令，靠 600ms 超时归零 | 一次请求 = **改服务端状态**，主循环持续发 |
| 容错 | 每个参数 `try/except int()` | 同（**保留**），且**每个参数独立**，写错一个不连累整条 |
| 响应 | 302（成功）/ 200 小页（失败） | 同（**保留**）：302 发不出去时退回 200 保底页 |

**为什么保留双层 try/except**：README 第 3 条。`_handle_cmd` 外层兜住
`_parse_query`/`_apply_cmd` 的任何异常，`_apply_cmd` 内部再逐参数容错；
**无论走哪条路径都一定有响应**（自检专门验证了 5 组垃圾参数 + 1 次"内部故意抛异常"）。

**为什么用 `m`/`a` 而不是沿用 `st`**：`st=180` 那套编码来自旧 JS 页，语义是
"瞬时方向"，和"动作状态"不是一回事。新参数更直白，也支持字符串别名
（`a=fwd` / `a=back` / `a=left` …），手机上手动改 URL 也能用。

### 3.5 状态：局部变量 → `st` 字典（基线 587~593 行）

```python
st = {'mode','action','stance','sp','seq','turn_t0','t_send','t_cfg','t_cmd','period','msg'}
```

**为什么**：状态要在 HTTP 处理、定时器、页面渲染三处共享，用 dict 传引用最省事
（MicroPython 里没有 dataclass，也不该用）。`msg` 是给状态栏用的一行"刚才发生了
什么"，让用户不用猜（比如"自动模式：动作无效，请先点【手动】"）。

### 3.6 `CMD_TIMEOUT_MS`：600 → **0（关闭）**

**为什么**：README 第三节第 2 条要求"点一下就一直走，**直到点停止**"，600ms 软超时
会把它变成"走 0.6 秒" —— 功能直接失效。

**代价（已在文件头写明）**：手机掉线时车会保持当前动作。安全网还剩两道：
FPGA 侧 500ms 看门狗（主循环崩了/帧停了就停车）+ 手动点【停止】。
想恢复旧行为：`CMD_TIMEOUT_MS = 600`，其余逻辑一行都不用改（`_tick()` 里那段
代码是完整的，只是被 0 关掉了）。

### 3.7 `srv.listen(2)` → **`listen(8)`**（基线 558 行）

**为什么**：README 第 11 条。浏览器会开 4~6 条空闲预连接，backlog=2 时新的
`/cmd` 可能连 SYN 都排队失败。

### 3.8 上电：不再强制手动 → **默认自动（`BOOT_MODE = 0`）**

**为什么**：基线在 `run()` 里开局就把 `0x20=1` 打开（基线 566~574 行）。
扩展版有真正的模式切换，默认值应该选**最安全的那个**：
- 自动 = 和 FPGA 自己的上电默认一致，本机**一帧 RC 都不发**，不存在"抢控制"；
- 想遥控必须显式点【手动】，避免"上电就接管，人还没准备好车就动了"。

页面会把自动模式画成黄色警示、运动按钮置灰，点运动按钮时状态栏直接提示
"请先点【手动】" —— 不会出现"点了没反应还以为坏了"。
（想开机即可遥控：`BOOT_MODE = 1`。）

### 3.9 新增 `_tick()`：主循环的周期性工作（基线 787~819 行的三段逻辑重写）

顺序：软超时（默认关）→ 转弯到点自动停 → 每 2s 重发 CONFIG → 20Hz RC 帧。

**为什么单独抽成函数**：基线把这三段直接写在 `while True` 里，混着 120 行 HTTP
处理，**没法在 PC 上测**。抽出来以后，自检脚本可以用假时钟 1ms 一步地驱动它，
把"自动模式 3 秒 0 帧""手动 1 秒 20 帧""转弯 360ms 停"全部变成可复现的断言。

### 3.10 新增 `_rc_frame()` / `_rc_values()`：**修掉 bit7 后退 bug**（详见第 9 节）

**为什么不用 `up.make_rc_cmd(steer, speed_byte, seq)`**：README 的表格这么写，但
`uart_proto.make_rc_cmd()` 内部有 `if sp > 100: sp = 100`，`0x80|40=168` 会被钳成
`100`，bit7 直接消失 → **按【后退】变成 100% 满速前进**。
改成自己组 3 字节载荷 + `up.pack_frame(up.TYPE_RC_CMD, ...)`（帧头/BCC/帧尾仍由
`uart_proto` 生成，协议实现只有一份，没有复制第二份协议代码）。
`pack_frame` 万一不可用时才退回 `make_rc_cmd`（丢后退标志，但不会崩）。
（README 后来追加的 §13 把"用 `pack_frame` 自己组载荷、别改协议库"定成了标准做法，
本实现与之一致，并通过了 §13 的 `00 A8 07` 校验。）

### 3.11 新增"立刻补帧"：切模式 / 停车 / 转弯到点

**为什么**：20Hz 意味着最坏要多等 50ms。点【停止】多滑 50ms 在 40% 速度下是
1.25cm，切自动时更是"FPGA 接管瞬间车还在按上一帧走"。所以：
- `_set_action()` 设完动作立刻发一帧；
- `_set_mode()` 切自动**之前**先发一帧 `steer=0 speed=0`（自检断言了这条顺序：
  `RC@0 -> CFG0@1`）；
- `_tick()` 里转弯到点也立刻补一帧，不等下一个 tick。

### 3.12 新增 `_send_resp()`：头部只在一处拼

**为什么**：`Content-Length` 必须是**字节数**（基线 757~765 行的注释记过这个坑）。
把"拼头部 + encode + 两次 `_send_all`"收敛到一个函数，`/h` 和 `/ver` 都走它，
就不会再有人漏 `encode()` 后取 `len(str)`。自检对 `/h`、`/ver` 都核对了
声明长度 == 实际字节数。

### 3.13 新增 `_http_one()`：把 HTTP 处理从 `while True` 里抽出来

行为与基线等价（`settimeout(0.02)` / 空请求直接关 / 四条路由），只是搬进函数，
`run()` 的主循环因此只剩 10 行。**没有任何行为改动**，纯结构重构。

### 3.14 `/ver` 探针扩展（基线 708~726 行）

保留原字段（`VER`/`PAGE_BYTES`/`FILE`），增加 `MODE`/`ACTION`/`STANCE`/`SP`/
`TURN_MS`/`SEND_HZ`/`CMD_TIMEOUT_MS`/`RESEND_MS`。
**为什么**：手机打开 `/ver` 就能同时确认"板上跑哪一版"和"板子自己认为现在是什么
状态" —— 排查"页面显示的和实际动作不一致"时，这两个信息必须能分开看。

### 3.15 `dry_run()` 扩展（基线 825~834 行）

除了打印 5 种动作的帧，还**断言**帧长 12 字节、且帧里的 speed 字节与预期一致
（专门用来抓 bit7 被钳掉）。PC 上 `python wifi_rc_ext.py` 就能跑。

### 3.16 保留不动的部分

`_send_all()`（逐字一致）、`_log()`、`DEBUG_HTTP=False`、`_loghttp()`、
`_setup_uart()`、`_setup_ap()`（含幂等/等驱动的兜底）、`_parse_query()` 的
"无白名单"实现、`SO_REUSEADDR` + `0.0.0.0:8080` + `settimeout(0.005)`、
`gc.collect()` 在 `run()` 开头、`CACHE-CONTROL: no-store`、302/200 双保险。

## 4. 关键设计决策（含为什么没选别的方案）

1. **状态放服务端，不放浏览器**（最大的一条）
   替代方案：继续用 JS 轮询 `/cmd`，把 `pressed` 换成 `latched`。
   否决原因：① README 第 6 条要求零 JS（手机可能不执行内联 script）；
   ② 手机锁屏/切后台时 JS 定时器会被冻结，帧断续，"保持"就变成"走一段"；
   ③ 页面刷新后浏览器侧状态丢失，和板子状态对不上。服务端保持则天然没有这些问题。

2. **默认自动 + 显式切手动**
   理由见 3.8。安全优先，且和 FPGA 上电默认一致，绝不出现"两个状态机抢控制"。

3. **转弯速度固定 40%，不受速度选择影响**
   `TURN_MS=360` 这个数是按 40%、R=115mm 算出来的（推导写在源码常量注释里）。
   如果转弯也用可调速度，360ms 就得跟着变，否则角度就不准了 —— 与其引入一张
   速度↔时长映射表（还要标定），不如把转弯固定成 README 指定的 40%。

4. **转弯结束是"停"，不是"恢复前进"**
   README 写的是"到时间自动停"。恢复前进需要记住转弯前的动作，多一份状态、
   多一类 bug（比如转弯途中点了停止），收益不明。要连走带转就再点一次前进。

5. **速度下限 10%**
   0% 的"前进"没有任何意义，却很容易被当成故障（状态栏显示前进但车不动）。
   要停有【停止】按钮。可调范围 10~`SPEED_CAP`(100)。

6. **`listen(8)`、`settimeout(0.005)`、空请求直接关** —— README 第 11/12 条原样照做。

7. **`/h` 的高亮只改边框色，不改背景**
   否则红色的【停止】在"当前生效"时会被改成绿色，语义反转。

## 6. 上板验证建议（手机操作，10 步）

> 板子不能请求自己（README 第 10 条），所以只能在手机上验。

1. `import wifi_rc_ext; wifi_rc_ext.run()` → 串口/`rc_boot.txt` 看到 `VERSION=2026-11-01-r10-ext`；
2. 手机连 `RobotRC` / `12345678`，打开 `http://<板子IP>:8080/h`（页面打不开就先用 `/ver`）；
3. 看状态栏：应为 **模式=自动（黄）、动作=停止、站立=高位、发帧=停发**；
4. 点【手动】→ 状态栏变 **模式=手动、发帧=20Hz 遥控帧**，FPGA 侧进手动；
5. 点【前进】→ 车持续前进；**松手不管它，10 秒后它应该还在走**（这条验证"保持"）；
6. 点【停止】→ 立刻停；
7. 点【后退】→ **必须真的是后退**（这条验证 bit7 修复；如果变成往前冲，立刻断电并回报）；
8. 点【左转 90°】→ 车身转约 90° 后自己停（用手机指南针或地砖估角，误差 ±13° 属正常）；
9. 点【降低】→ 蹲下；【升高】→ 站起；等 2 秒以上再点一次，确认重发没打架；
10. 点【自动】→ 状态栏变回自动、发帧=停发，此时点【前进】应无动作且状态栏提示"请先点【手动】"。

## 7. 已知限制 / 风险

| 限制 | 说明 / 缓解 |
|---|---|
| 转弯角度有量化误差 | 20Hz + HTTP 抖动 → 实际 360~410ms（约 ±13°）。要更准就把 `SEND_HZ` 提到 50，或改由 FPGA 定时 |
| 手机掉线车不会自己停 | `CMD_TIMEOUT_MS=0` 的必然代价（见 3.6）。改回 600 即可恢复 |
| 状态栏是"最后渲染时"的状态 | 零 JS 的必然结果。转弯这类 360ms 的动作，页面显示"左转 90°"时可能已经停好了，点【刷新状态】即可看到"停止" |
| 里程/轮速没有闭环 | 360ms 是开环定时，电池电压下降/地面打滑都会影响角度 |
| 页面不能显示实时遥测 | 没有 JS 就没有轮询；要做就得开 meta refresh 或另开接口（本版没做） |

## 9. ⚠️ 附带发现：基线/生产版的"后退"是坏的（已单独上报）

**现象**：按【后退】会以 100% 速度**前进**。

**链路**：
1. `uart_proto.make_rc_cmd()` 内部有 `if sp > 100: sp = 100`；
2. 基线 814 行、生产版 `arm/wifi_rc.py` 814 行都是
   `up.make_rc_cmd(steer, (rev << 7) | mag, seq)`；
3. 后退时 `rev=1`、`mag=40` → `speed_byte=0xA8=168` → 被钳成 `100` → bit7 消失。

**实测证据**（CPython + 本目录 `uart_proto.py`）：

```
make_rc_cmd(0, 0x80|40, 7)          -> 载荷 00 64 07   ← speed=100，bit7 没了
pack_frame(0x05, bytes([0,0xA8,7])) -> 载荷 00 A8 07   ← 正确
```

**README §13 的硬性校验（本产物已通过）**：

```
_rc_frame(up, 0, 0xA8, 7) 的载荷 = 00 A8 07   ✅（期望 00 A8 07）
对照 up.make_rc_cmd(0, 0xA8, 7)   = 00 64 07   ✗
```

**为什么一直没暴露**：基线 JS 页注释写着"FPGA 侧 motion_decision 暂不支持负速度
→ 目前等同停车"，那段时间按后退本来就不动，钳位问题被掩盖了；后来 RTL 加了
`dir_inv`、注释改成"后退已支持"，这条旧路径就成了定时炸弹。

**本产物的做法**：见 3.10（自己组 3 字节载荷 + `pack_frame`，即 README §13 指定的
做法；**没有**去改协议库 `make_rc_cmd`）。
**生产版的修法**：父 agent 已在本任务期间按同样思路改了 `arm/wifi_rc.py`（36657
字节），不属于本任务的产出，此处只做记录。
