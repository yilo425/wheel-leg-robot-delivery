# 第一部分：工具链打通

## 1.1 ★★★ Gowin 不能处理中文路径（**本项目的头号大坑**）

**现象**：
```
alog error: failed to open log file:
  'C:/Users/??/AppData/Local/GowinSemi/IDE/cache/sh.log'
```

**根因**：`gw_sh.exe` 用当前工作目录派生日志文件路径。工作区在
`C:\Users\忆洛\...` 时，`忆洛` 在当前代码页（GBK）下无法正确转换，
变成 `??`，于是日志路径不存在。

**影响**：
- 工具**能跑**（综合、布局布线都完成了），但日志写不出来
- **工程目录也读不了中文** —— 工程建在中文路径下会直接失败

**解法**：**所有 Gowin 相关的工作都在纯 ASCII 路径下做。**

**我们最终的做法**：把整个仓库从
```
C:\Users\忆洛\Documents\deepseek-harness\default-workspace\robot_project
```
迁到
```
D:\dsh-ws\robot_project
```

**顺带收益**：迁移后连 ModelSim 的工作库也能放进仓库里
（`robot_project\.simlib\work`），**不再需要任何额外写权限**。

> ⚠️ **团队成员注意**：你自己用 Gowin GUI 建工程时，
> **千万不要建在含中文的路径下**（比如桌面路径含中文名）。

## 1.2 ★★★ ModelSim 同样不能在中文路径建工作库

**现象**：
```
init_dbinfo() DATABASE ERROR:
  (sqlite3_open C:/Users/????/.../work/_lib.qdb): unable to open database file
sqlite3_open_v2: No such file or directory
mtilibWrite(): INTERNAL ERROR: Unexpected null object encountered
** Fatal: (vlog-9) Problem while writing internal20180930A file ".../work/_temp/vlogXXXX"
```

**根因**：系统 ACP = 936（GBK）。ModelSim 把路径**按 ANSI 传给 sqlite**，
而 **sqlite 按 UTF-8 解释** → 目录不存在。

**关键细节**：`vlib` 自己**能**在中文路径建库并写 `_info`
（所以你会以为"路径没问题"），**只有 sqlite 那一步挂**。

**已试过但无效的办法**（别再试了）：
- `vlib -type flat`
- `-work ./work`（相对路径仍被解析成绝对路径）
- `modelsim.ini` 里 `work = work` / 绝对路径映射
- `subst W: <workspace>`（沙箱拒）
- .NET `DefineDosDevice`（沙箱拒）
- 用户目录 8.3 短名（`C:\Users\忆洛` 这一段**没有**短名）

**解法**：工作库必须放纯 ASCII 路径。我们用 `D:\dsh-ws\robot_project\.simlib\work`。

## 1.3 ★★ `vsim` 报 "Error loading design" 时，要看 `vopt`

**最没用的错误信息。** `vsim` 只给一行：
```
Error loading design
```

**真实错误只有 `vopt` 会报**：
```powershell
vopt -work <lib> <tb_name> -o tb_opt
```

**而且 `vopt` 还会检查 `vlog` 不检查的东西**：
- **端口名是否匹配**
- **参数名是否匹配**
- **位宽是否匹配**
- **例化是否完整**

> `vlog` 编译通过 ≠ 能跑。**必须过 `vopt`。**

**本项目自己写了 `tools/check_instantiations.py` 做静态交叉检查**，
就是为了在跑之前发现这类问题。

## 1.4 ★★ `vsim` 必须加 `-voptargs="+acc"`

当 tb 用了内存引用（`dut.some_signal`）时，没有这个参数
优化器会把那些信号删掉，然后 `vsim` 报 `Error loading design`。

项目自带的 `run_sim.do` 里已经有这个参数，**自己手写命令时别漏**。

## 1.7 ★★ License：绑定 MAC，分 NODELOCK / FLOATING 两类

**license 文件格式**：
```
MODE = NODELOCK          # 节点锁定（绑一台机器） 或 FLOATING
TYPE = STD               # Standard（需 license） / 教育版不需要
HOST_ID = C4C6E6644513   # 绑定的网卡 MAC（12 位十六进制，无分隔符）
EXP_DATE = 2027-10-14
```

**Gowin 期望的 license 路径**（写死在 `IDE\bin\gwlicense.ini` 里）：
```
[license]
lic="C:/Gowin/gowin.lic"
```

**申请要点**：
- 地址：`https://www.gowinsemi.com/en/support/license/`
- **MAC 格式**：申请表单要**冒号分隔**（`C4:C6:E6:64:45:13`），
  不是 12 位连写。填错会报"格式不正确"
- **Host ID 就是以太网的 MAC**（不是 WLAN、不是蓝牙）
- 1-3 个工作日，绑 MAC，**换机器要重新申请**

**小梅哥给的应急 license**（`gowin_E_D4D853392AD8.lic`）：
- 绑的是**别人的 MAC**，用不了
- **用法是改自己的网卡 MAC 去迁就它**：
  网络设置 → 以太网 → 属性 → 配置 → 高级 → **网络地址**
  → 填 `D4D853392AD8`（**无分隔符**）
- ⚠️ 小梅哥自己提醒："改网卡号有时候会和电脑上其他软件的授权冲突，不是长久之计"
- **本地网卡 MAC 是 12 位连写；高云申请表单是冒号分隔 —— 两个地方格式不一样**

## 1.9 `programmer_cli` 常用操作

| 操作 | 命令 | 退出码 |
|---|---|---|
| 扫下载器 | `--scan-cables` | 0 成功 / 48 没找到 |
| 扫 JTAG 链 | `--scan` | 0 / 49 |
| **读器件信息**（最常用，只读） | `--device GW5AT-138 --run 0 --cable-index 1` | 0 |
| **SRAM 烧录**（不校验） | `--device GW5AT-138 --run 2 --fsFile xxx.fs --cable-index 1` | 0 |
| **SRAM 烧录+校验** | 同上把 `--run 2` 换成 **`--run 4`** | 0 / **18 = Verify Failed** |
| SRAM **回读**（不是烧写！） | `--run 3` | 0 |

**★ `--run` 是操作索引 —— 网上流传的那张表和 V1.9.12 实际不一致，别再照抄**。
以 `programmer_cli.exe --help` 为准（V1.9.12 build 2558 实测）：

```
0: Read Device Codes        1: Reprogram
2: SRAM Program             3: SRAM Read            ← 回读，不是烧写
4: SRAM Program and Verify  5/6: embFlash Erase,Program[,Verify]
7: embFlash Erase Only      8/9: exFlash Erase,Program[,Verify]
10: exFlash Bulk Erase      11: exFlash Verify      12: exFlash Erase,Program in bscan
```

> ⚠️ **踩过的坑（2026-10-17）**：旧版本文档把 `--run 3` 写成
> "SRAM Program and Verify"，实际它是 **SRAM Read** ——
> 跑完会打印 `Reading SRAM: [####] 100%` 并以 0 退出，
> **看起来成功了，但板子里什么都没变**。（判断依据：User Code / Status Code 前后不变。）
> 真正的"烧写+校验"是 **`--run 4`**。

> ⚠️ 另外：`--run 4` 在本板（GW5AT-138）上实测报 **`Error: Verify Failed`（退出码 18）**，
> 而同一次比特流用 **`--run 2`（只烧不校验）退出码 0、User Code 确实变了** —— 
> 说明**写入是成功的，失败的是回读比对**。可能原因：比特流按 `-device_version B` 综合，
> 而芯片实际版本（B/C）未知；或该器件的 SRAM 回读内容与比特流文件格式不能直接逐字节比。
> **结论：烧 SRAM 用 `--run 2` 看现象为准；`--run 4` 的 Verify 失败不代表没烧进去。**

## 1.11 ★★★ 中文用户名会从**另一个地方**咬人：`%TEMP%` → `vsimk` 退出码 7

**现象**（2026-10-15，把全量回归的输出用 PowerShell 管道接走时）：

```
# RUN tb_top_i2c_share
** Error: Error while reopening stdout stream!
   Error: couldn't open "C:/Users/????/AppData/Local/Temp/VSOUTdrxzds":
   filename is invalid on this platform
** Fatal: vsimk is exiting with code 7.
```

**根因**：ModelSim 批处理（`vsim -c`）在 stdout 被**管道**接走时，会把溢出内容
写到 `%TEMP%` 下一个 `VSOUTxxxx` 文件；本机 `%TEMP% = C:\Users\忆洛\AppData\Local\Temp`，
中文用户名被按 ANSI 转成 `????` → 路径非法 → **`vsimk` 直接退 7**。

**为什么难查**：它和 tb 的代码**完全无关**，但症状极像"某条 tb 崩了"：
跑一半就断，**最后几条 tb 的结果文件是空的或根本没生成**。
而且**输出量小的时候不触发** —— 单跑一条 tb、或只跑前几条时一切正常，
只有输出量攒够（本工程是第 13 条 tb 起）才炸。

**对策**（两条都要）：

```powershell
# ① 把临时目录指到纯 ASCII 路径
$env:TEMP = 'D:\dsh-ws\_tmp'
$env:TMP  = 'D:\dsh-ws\_tmp'
New-Item -ItemType Directory -Force -Path $env:TEMP | Out-Null

# ② 输出用**文件重定向**，不要用 PowerShell 管道 | Select-String ...
cmd /c "set TEMP=D:\dsh-ws\_tmp&& set TMP=D:\dsh-ws\_tmp&& `"$VSIM`" -c -do run_sim.do > sim_full.log 2>&1"
```

**顺带**：`run_sim.do` 里每条 tb 是一次**嵌套 vsim**，结果文件是异步写完的 ——
跑完要**等 10~20 秒**再读，否则会看到"最后几条 tb 结果文件是空的"这种假故障。

# 第二部分：Verilog / RTL 编码

## 2.1 ★★ 不能对 `parameter` / `localparam` 做位选

```verilog
// ❌ Verilog-2001 非法（这是 SystemVerilog 的语法）
localparam integer DEB_CYC = 1000;
if (cnt >= DEB_CYC[31:0]) ...

// ✅ 声明成定宽向量，就不需要位选
localparam [31:0] DEB_CYC = 1000;
if (cnt >= DEB_CYC) ...
```

**ModelSim 能过，综合器可能拒绝** —— 而且报错信息很难懂。

**本项目踩过的地方**：`uart_tx.v`、`uart_frame.v`、`encoder_decode.v`、
`pwm_motor.v`、`uart_rx.v`、`reset_sync.v`、`servo_lift.v`。

**静态检查**：`tools/rtl_lint.py` 会报这个。

---

## 2.2 不能在 `always` 块里声明 `wire`

```verilog
// ❌ 非法
always @(*) begin
    wire cross_ok = path_clear && ...;   // 编译不过
    ...
end

// ✅ 放到 always 外面
wire cross_ok = path_clear && ...;
always @(*) begin ... end
```

---

## 2.3 task 的端口不能写 `input wire clk;`

```verilog
// ❌ 报 (vlog-13069) near "wire": syntax error，还会引发一串级联错误
task foo;
    input wire clk;
    ...
endtask

// ✅ 去掉 wire
task foo;
    input clk;
    ...
endtask
```

---

## 2.4 ★★ task 的 `input` 是**值拷贝**，不是引用

```verilog
// ❌ 会挂死：clk 是进 task 那一刻的值拷贝，@(posedge clk) 永远等不到边沿
task wait_edge;
    input clk;
    begin
        @(posedge clk);
    end
endtask

// ✅ 用内联的 @(posedge clk_bypass)，或者不把时钟传进 task
```

**这个坑很隐蔽** —— tb 会直接挂住（看起来像"死循环"）。

---

## 2.5 声明顺序（先用后声明会生成隐式 1 位网）

Verilog 里用了未声明的标识符，会**自动创建隐式 1 位 wire** ——
不报错，但位宽错了，行为诡异。

**静态检查**：`tools/check_decl_order.py`

**本项目踩过**：`top.v` 里 `wire [2:0] state;` 在 393 行被用、424 行才声明。

---

## 2.6 每个 `always` 都要有复位分支

**低有效复位**，全项目统一。

---

## 2.7 每个等待都要有超时

**项目铁律**：不能有"无限等"的状态。

```verilog
if (done)          nstate = NEXT;
else if (t >= TMO) nstate = S_ESTOP;   // ← 必须有
```

---

## 2.8 安全逻辑不依赖上层

急停直接组合进使能输出：

```verilog
assign motor_enable = motor_en_r & ~estop;   // 0 拍延迟
```

**⚠️ 代价**：这是一条**纯组合路径**（输入脚 → 逻辑 → 输出脚），
在时序约束里会是最长路径之一。**这是刻意的取舍**，
代码注释里写明"不要改成寄存器输出"。

# 第三部分：测试方法

## 3.1 ★★ 时间尺度：1ms = 50000 拍（@50MHz）

**踩过的坑**：
```verilog
CROSS_MIN_MS = 800;   // 800ms
...
repeat (60) step;     // ← 只走了 1.2us，差 4 个数量级
```

**正确做法**：写一个 `wait_ms` task
```verilog
localparam integer TB_MS_TICKS = CLK_FREQ_HZ / 1000;

task wait_ms;
    input integer n;
    integer k;
    begin
        for (k = 0; k < n * TB_MS_TICKS; k = k + 1) step;
    end
endtask
```

**用 `for` 不用 `repeat`** —— `repeat` 的参数是 32 位整数，`n` 大时乘法可能溢出。

---

## 3.2 ★ 时间常数要**拉开**，否则检查点落空

**踩过的坑**：`CROSS_MIN_MS = 1`、`LIFT_SETTLE_MS = 1`，
然后 `wait_ms(2)` 去检查"现在应该在 LP_DOWN 阶段" ——
**结果状态机 2ms 内一路走完回到 AUTO 了**，检查到的是 `LP_IDLE`。

**解法**：让相邻的时间常数**差一个数量级**。

---

## 3.3 ★★ **结果文件时间戳比源码旧 = 陈旧结果**

**踩过的坑**：
- 改了 tb，跑一遍，看到 `RESULT: PASS`，很高兴
- **实际上是上一轮的旧文件** —— 新 tb 因为编译错误根本没跑起来

**防呆**：
```powershell
Remove-Item sim\*_result.txt -Force     # 跑之前先删
& vsim.exe -c -do run_sim.do
Start-Sleep -Seconds 3                  # 嵌套 vsim 异步写文件，等几秒再读
```

---

## 3.4 ★★★ **tb 里的理想信号会掩盖物理现实**

**最典型的例子（限位开关极性 bug）**：

- 引脚表里 `lift_done` 配了**上拉**（常开触点，未按下读 1）
- 但 `main_fsm` 写的是 `if (lift_done)`（高有效）
- **→ 一进 `LP_UP` 就误判"已到位"**，腿根本没抬

**为什么仿真发现不了**：tb 里直接 `lift_done = 1'b1;`，
**完全绕过了"上拉 + 常开开关"这个物理现实**。

**教训**：**tb 驱动的是"理想化的物理信号"时，要确保极性和真实硬件一致。**
最好的办法是**在 tb 里也用和硬件一样极性的信号**。

---

## 3.5 测脉冲宽度要从**边沿**开始

```verilog
// ❌ 如果调用时正好在高电平中段，会测到半截脉冲
while (lift_pwm !== 1'b1) step;
meas = 0;
while (lift_pwm === 1'b1) begin step; meas++; end

// ✅ 先等一个完整周期，回到上升沿再测
while (lift_pwm === 1'b1) step;      // 等当前高电平结束
while (lift_pwm !== 1'b1) step;      // 等下一个上升沿
meas = 0;
while (lift_pwm === 1'b1) begin step; meas++; end
```

**实测症状**：期望 2000 拍，测到 1899 —— **正好差一个"从哪里开始"的量**。

# 第四部分：脚本与运行环境

## 4.1 ★★ 含中文的 `.ps1` 必须有 UTF-8 BOM

**踩过的坑**：用 `edit` 工具改 `.ps1` 后，**BOM 被丢掉了**
→ PowerShell 按 **GBK** 读中文注释 → **解析失败** →
脚本没真正执行（**但退出码可能还是 0**）。

**症状**：脚本"跑了"但生成的 `.do` 文件是旧的。

**检查**：
```powershell
$b = [System.IO.File]::ReadAllBytes($path)
"有 BOM: $($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)"
```

**修复**：
```powershell
$t = [System.IO.File]::ReadAllText($f, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($f, $t, (New-Object System.Text.UTF8Encoding($true)))  # $true = 带 BOM
```

**⚠️ `.v` 文件相反 —— 必须 UTF-8 无 BOM**。

---

## 4.2 ★★ PowerShell 变量大小写不敏感

**踩过两次的坑**：
```powershell
$R = 'C:\path\to\repo'          # 仓库路径
foreach ($x in $list) {
    $r = Get-Content $rf          # ← $r 覆盖了 $R！
    $rf = "$R\sim\..."            # ← 下一圈 $R 变成数组，路径成垃圾
}
```

**症状**：第一圈正常，**第二圈开始全部找不到文件**。

**解法**：用不会冲突的名字（`$repoRoot` / `$lines` / `$content`）。

---

## 4.3 ★★ `.sdc` / `.tcl` 必须纯 ASCII

**根因**：Gowin 按**系统代码页（中文 Windows 上是 GBK）**读 `.sdc`/`.tcl`。
UTF-8 中文注释会变乱码，**乱码还可能被当成语法错误**。

**已发生**：`led_test.sdc` 的中文注释全烂成 `????`。

---

## 4.4 `.sdc` 的三个具体坑

### ① 注释符是 `#` 不是 `//`

SDC 是 Tcl。`led_test.sdc` 用了 `//`，**Gowin 恰好没报错**，
但换任何别的工具（Vivado / PrimeTime）都会挂。**别学它。**

### ② `get_clocks` 要写花括号

```tcl
# ❌
set_false_path -from [get_clocks clk_50m]
# ERROR (TA2000): 'syntax error' near token 'clk_50m]'

# ✅
set_false_path -from [get_clocks {clk_50m}]
```

### ③ IO 延迟不能把时钟周期占满

```tcl
create_clock -period 20                    # 20ns 时钟
set_input_delay  -max 10 [get_ports {...}] # 10ns
set_output_delay -max 10 [get_ports {...}] # 10ns
# → 10 + 10 = 20ns，逻辑一点余量都不剩
# → 急停那条组合路径报 -5.484ns 负 slack
```

**改成 `-max 5`** 之后满足（slack +0.158ns）。

**⚠️ 深一层**：0.158ns 余量只有 **0.8%**，很险。
最长的路径在 `main_fsm` 的大组合 `case` 块里。
**可以考虑把 `main_fsm` 的输出打一拍**（50MHz 下多一拍无所谓）。

---

## 4.5 `[math]::Format` 不存在

```powershell
# ❌
[math]::Format('{0:N0}', $n)
# ✅
'{0:N0}' -f $n
```
`Format` 在 `[string]` 上，不在 `[math]` 上。

---

## 4.6 `.Replace()` 是**静默失败**

```powershell
$t.Replace($old, $new)   # 如果 $old 不匹配，什么都不做，也不报错
```

**防呆**：
```powershell
if ($t.Contains($old)) { $t = $t.Replace($old, $new); $n++ }
else { "  [!] 锚点没匹配" }
```

---

## 4.7 ★ CRLF vs LF 会让多行替换失败

用 `@'...'@` here-string 写多行锚点，但文件的换行符不同 → **不匹配**。

**解法**：用 `edit` 工具；或用单行锚点；或显式写 `` `r`n ``。

## 4.8 ★ `robocopy /MIR` 会**删掉**目标里的文件

**踩过的坑**（两次）：

1. `sim/*.do` 是**生成物**，从旧仓库 `/MIR` 到新仓库时
   **覆盖了新仓库里重新生成的版本**（路径指向不对了）→ 回归跑出 0/11
2. **更危险**：如果目标仓库有独立工作，`/MIR` 会**直接删掉**

**安全做法**：

```powershell
#                     ↑ 排除这些目录        ↑ 排除生成物
```

**⚠️ 现在新仓库领先（有 TOF 集成），不要再从旧仓库往回同步。**

# 第五部分：硬件与采购

## 5.1 ★★★ 编码器 5V 输出会**打死** FPGA 的 3.3V IO

**FPGA 的 IO 是 LVCMOS33**，输入绝对最大值约 3.6V。

**常见霍尔编码器**：供电 5V → 输出 5V 方波 → **直接接进 FPGA = IO 长期过压**。

**这比接错线更隐蔽**：一开始可能"能用"，IO 在慢慢损坏，
**几天后才失效，根本查不出来**。

**三种解法**（按推荐）：
| 方案 | 做法 |
|---|---|
| **① 编码器用 3.3V 供电** | 大部分霍尔编码器 3.3~5V 都支持 ✓ **首选，问商家确认** |
| ② 加电平转换 | TXS0108E / 74LVC245（8 路，¥5） |
| ③ 分压电阻 | ❌ 边沿变慢，高速丢计数 |

**我们买的 Wheeltec MG310 确认是 3.3-5V 供电** ✓ 不用转换。

**⚠️ 到货后第一件事**：**量编码器输出高电平**（别直接插 FPGA）。

---

## 5.2 ★★ 舵机必须独立供电

**MG996R 堵转 2.5A**，4 个同时动可达 **10A**。
和 FPGA 共用一路 → 电压跌落 → **FPGA 复位**。

**这是这类机器人最常见的"莫名其妙重启"原因。**

**要求**：
- 独立 5V/**≥5A** 降压
- **并 1000µF 以上电容**
- 线径 ≥22AWG
- **所有 GND 共地**

---

## 5.3 ★★ 舵机不能长期承重

腿"蜷缩"是默认状态、占 99% 时间。如果整车重量一直压在舵机上：
- 持续发热
- 抖动（堵转电流大）
- 缩短寿命甚至烧毁

**必须做**：
1. **腿到极限位置要有机械止挡**（让重量走结构不走舵机）
2. 或加扭簧/气弹簧分担
3. 或腿用自锁机构

**这一条做不好，跑 10 分钟舵机就烫手。**

---

## 5.4 电机电压要和电池匹配

**我们的 MG310 额定 7.4V**（不是 12V！）。

| 方案 | 问题 |
|---|---|
| 3S（11.1V）直供 | ⚠️ 超压 50% |
| 3S + 可调降压设 7.4V | ✓ 可以，但多一个模块 |
| **2S（7.4V）** | ✓ 正好，且 FPGA 板 8.4V 也在 6-12V 规格内 |

**注意**：ACG720 板规格 **6~12V**，3S 满电 **12.6V 超了**。

---

## 5.5 轮子孔径必须匹配电机轴

**最容易买错的一项。**

MG310 是 **3mm 光轴**（不是 D 型轴）→ 轮子要选 **3mm 孔**，
而且**光轴上打顶丝容易滑** → 用带顶丝的金属轮毂，或在轴上磨一个小平面。

---

## 5.6 编码器必须是**增量式正交 AB 相**

**不能是**：
- 只有单相脉冲输出（测不出方向）
- 绝对式 / 串行（如 AS5600 I2C，需要专门驱动）

**代码里是 4 倍频正交解码**（`encoder_decode.v`），需要完整的 AB 相。

---

## 5.7 PWM 可以限速（电压不匹配的兜底）

```verilog
// pwm_motor.v: duty_in=64 即 50%，满量程 128
// motion_decision.v: LIMIT_DUTY = 120  → 93.75%
```

**3S 11.1V × 占空比 67% ≈ 等效 7.4V** → 改 `LIMIT_DUTY: 120 → 86` 就行。

**但**：这是兜底方案，**优先用硬件（可调降压）解决**。

---

## 5.8 不要买整机（比赛红线）

比赛题目是「**基于高云 FPGA** 的机器人」。
**买成品机器狗 = 主控是别人的 = 评审判不合格。**

**正确姿势**：买**机械本体**（结构件/电机/舵机），**主控用 FPGA 自己搭**。

---

## 5.9 电池容量怎么选

**先算功耗**（我们这台）：
```
待机（只上电）：   FPGA 3W + ARM 2.5W ≈ 5.5W
正常行驶：        加电机 ≈ 15-20W
抬腿动作：        加舵机 ≈ 9W
```

**3000mAh / 3S**：
```
能量 = 11.1V × 3Ah = 33.3Wh
待机 6 小时 / 行驶 1.7 小时
重量 ≈ 250g
```

**3000mAh 是甜点** —— 比赛演示只要 15-30 分钟，余量 3 倍以上。

**⚠️ 别买太大**：整车才 1.5kg，5000mAh 电池重 400g，
**重量直接加到舵机负载上**。

**⚠️ 比容量更重要的是 BMS 限流值**：容量大 ≠ 能出大电流。
需要 **≥6A** 的持续输出（急启动峰值会到 4-6A）。

### `check_always_reset.py` 说明（2026-10-18 新增）

规则 2.6「每个 always 都要有复位」以前只写在文档里，而**编译器不会报**：

```verilog
always @(posedge clk) begin
    cnt <= cnt + 1;      // 忘了复位 -> 上电后一路 X
end
```

上板表现是「偶尔启动后不工作、重新上电又好了」，极难查。现在变成机器检查。

- 只看**时序** always（`posedge`/`negedge`）；组合 `always @(*)` 不需要复位
- 判定窗口：always 之后 8 行内要出现 `if (!rst_n)` / `if (rst_n == 1'b0)` 之类
- **误报处理**：正则必须容忍前缀，本项目同时用 `rst_n` 和 `arst_n`
  （第一版写成 `!\s*rst`，把 `!arst_n` 判成"没复位"→ 误报 2 处）
- **白名单**：确实不需要复位的写法，在 `always` 上一行加
  `// check_always_reset: waive -- <理由>`
  目前只有一处：`uart_frame.v` 的**存储器写口**（给整块 RAM 加复位要一个巨大的 mux，
  而读之前一定被写过）。

> **误报比漏报烦人得多** —— 一个天天误报的检查会被关掉，那就等于没有。
> 所以这个脚本刻意只做"块内前 8 行有没有 rst 字样"的文本判定，宁可漏报。

# 第七部分：协作与子代理

## 7.1 子代理**隔离上下文**，适合干重活

**实测数据**：一个子代理写 `i2c_master.v`(513行) + `tof_driver.v`(576行)
+ `tb_tof_driver.v`(617行)，花了 **52.4M 令牌 / ¥1.85**。

**如果主会话自己做**：会吃掉大量上下文（可能 100M+）。

**结论**：**自包含的重活派子代理** —— 省钱 + 不污染主会话。

## 7.2 子代理**没有提权能力**（重要）

**实测**：子代理会话 sandbox = workspace-write，**工作区外一律不可写**，
而且**审批被禁用**，无法提权。

**所以**：需要写工作区外（比如 ModelSim 的 ASCII 工作库）时，
**子代理做不了** —— 要主会话（有提权）来做。

**分工建议**：
```
子代理：写代码 + tb + 跑静态检查（这些在工作区内）
主会话：跑 ModelSim（需要 ASCII 工作库）+ 综合 + 集成
```

## 7.3 ★ 给子代理的任务书要**写全项目约定**

因为子代理**看不到你的对话**，必须把坑重述一遍：
- Verilog-2001 限制（不能位选 parameter、不能 always 里声明 wire…）
- 编码要求（UTF-8 无 BOM）
- ModelSim 用 ASCII 工作库
- **只新增文件，不许改现有文件**（尤其是 `top.v`）
- 交付要求：静态检查**贴原始输出**、给编译命令、说明不确定的地方

## 7.4 ★★ **"如实报告失败"是值得表扬的行为**

那个子代理**一次都没编译过**，但它：
- ✅ 明确说"**我没有拿到 RESULT: PASS，不假装有**"
- ✅ 给出了**实测证据**（ACL 有 Modify 但仍被拒 → 是沙箱不是 ACL）
- ✅ 列了**试过但无效的办法**（subst / DefineDosDevice / 8.3短名 / `vlib -type flat`）
- ✅ 说明了**不确定的地方**（VL53L0X 初始化实现到哪一级、为什么不写全表）
- ✅ 给出**可直接执行的命令**

**结果**：它写的代码**第一次编译就 0 error 0 warning，第一次仿真就 43/43 PASS**。

**教训**：**鼓励"如实报告不确定"，比假装通过有价值得多。**

`doc/interface_spec.md` 里先写死接口约定，再实现模块。

## 8.5 `VREF_FULL` 的标定方法（换电机必看）

```verilog
// rtl/top.v
parameter integer SPEED_WIN = 500_000;   // 10ms @50MHz
parameter integer VREF_FULL = 69;        // 当前值
```

**公式**（`encoder_decode.v` 是 **4 倍频**）：
```
每轮一圈的计数 = PPR × 4 × 减速比

VREF_FULL = (目标RPM / 60) × (PPR × 4 × 减速比) × 窗口秒数
```

**当前电机**（MG310，13 线，1:20，额定 400 RPM）：
```
每圈 = 13 × 4 × 20 = 1040
VREF = (400/60) × 1040 × 0.01 = 69.3 → 69
```

## 8.6 三个"看起来能行但实际不行"的陷阱

# 9. 上板联调实录（2026-10-18）

这一节全是**"仿真全绿、上板却不对"**的真实案例，比任何教科书都值钱。

## 9.1 ★★★ 烧录前必须确认 `.fs` 是**刚编出来的**

**现象**：ARM 那侧 2 秒内数到 `uart_tx(C19)` **零跳变**、电平恒高（用 GPIO 直接采样证实）。
而同一条 RTL 在仿真里 telemetry 正常（`tb_telemetry_check` 收到 26 字节）。

**处理**：只改了 `led[0]` 的一个接法 → 重新综合 → 重新烧录 → **`uart_tx` 立刻正常**
（2 秒 598 次跳变，1% 占空比，正好 20 帧 × 1.9ms）。

**教训**：
- `programmer_cli` 只认**你给的那个 `.fs` 文件**，它不会告诉你这个文件是不是过期了。
- 烧完看一眼 `User Code`，和刚综合出来的期望值对一下；或者干脆
  **每次烧之前先删掉旧 `.fs`**，让它"必须重新生成才存在"。
- 别把"仿真过了"当成"板上会过" —— 中间还隔着"比特流是不是这一份"。

## 9.2 ★★★ K230（CanMV）的 `uart.any()` **永远返回 1**

```python
n = uart.any()      # 不管缓冲里有多少字节，都返回 1
d = uart.read(n)    # 于是每次只能拿到 1 个字节
```

实测：3 秒里 `reads == bytes == 17043`，每次都是 1 字节；而 `uart.read()`（**不带参数**）
一次性返回 6610 字节。

**正确写法**：
```python
d = uart.read()    # 不带参数 = 把缓冲里所有字节都拿走
if d: feed(d)
```
**教训**：`any()` 看着像"有多少字节可读"，在 K230 上不是。凡是"按 `any()` 决定读多少"的
代码，在这里都会退化成 1 字节/次 —— 不丢数据，但慢得离谱。

## 9.3 ★★★ 增量串口解析器：**没找到帧头时不能清空整个缓冲**

错（我写的，调试脚本里踩的）：
```python
i = buf.find(b'\xaa\x55')
if i < 0:
    buf = b''        # ← 错！半个帧头也会被丢掉，一字节一喂永远凑不齐一帧
```
对：
```python
if i < 0:
    buf = buf[-1:]   # 只可能留着"半个帧头"，最多 1 字节
```

配合 9.2 的坑，这两个 bug 叠在一起的表现是：**线上有数据、帧头帧尾都在，但解析出 0 帧**。

## 9.4 ★★ 给人看 LED 时，必须给出**完整编码表**

我说过"`D5` 亮 = 状态机在 AUTO"，**这是错的**：
`D5` 只是 `state_dbg[1]`（bit 1），而 `state=2(010)` 和 `state=6(110)` **D5 都亮**。

结果用户看到 D5 亮就以为进了 AUTO，实际还在 ESTOP，白折腾两轮。

**教训**：`state_dbg` 是**二进制编码**，不是"每个灯一个状态"。
给非专业用户描述时，要么给完整对照表（D6/D5/D4 组合），要么**只在"唯一"的灯上下断言**。

## 9.5 ★★ 状态机的"退出条件"会让实验设计失效

`S_AVOID` 只有 `path_clear`（前方够空）才能退回 `AUTO`，否则 **5 秒后超时 → ESTOP**。
`S_ESTOP` 又需要**按两次 S0**（ESTOP→IDLE→AUTO）。

所以我设计的"改阈值 → 看它退回 AUTO"的实验**根本不可能成功**：物体一直挡在 5cm，
`path_clear` 永远不成立。

**教训**：设计上板实验前，先看清 FSM 的**进入/退出条件**和图；
否则实验现象会被"退出条件不满足"污染，误判成功能坏了。

## 9.6 ★★ tb 里声明了 `wire uart_tx` 但**从不使用** = 零覆盖

`tb_top_integration` 里有 `wire uart_tx;` 并接到 DUT —— 但**没有任何断言读它**。
于是 telemetry 发送通路在整个回归里**从来没被验证过**，19 条 tb 全绿也说明不了任何事。

**补法**：`sim/tb_telemetry_check.v` —— 用**和硬件完全一致的参数**
（`TOF_ENABLE=1 / TOF_IF=1 / IMU_ENABLE=0`）例化 `top`，只干一件事：监视 `uart_tx`
有没有跳变、能不能解出完整字节。

**教训**：`wire x;` + `.port(x)` 不算测试。**只有被断言过的信号才算**。

## 9.7 ★ 诊断固件比"猜"快得多

这轮写了两个**独立的小工程**（`tools/fpga_build/beacon` / `keymon`），
各有自己的 `.v/.cst/.sdc/build.tcl`，~1 分钟就能综合烧录：

| 工程 | 作用 | 结论 |
|---|---|---|
| `beacon` | C19 输出 ~3Hz 方波 | 2 秒 24 次跳变 → **线是通的**，排除了接线问题 |
| `keymon` | 4 个灯显示 3 个按键的实时电平 | 一眼看出某个键到底有没有反应 |

**教训**：当"线/引脚/按键"是嫌疑对象时，**别用产品固件去猜** ——
写个 30 行的专用固件，把那个信号直接怼到灯上或方波上，一分钟出结论。

# 10. 一次完整的"电机不转"电气排查（2026-10-18 夜）

这一节值得完整读一遍 —— 里面有三条**反直觉**的坑，每一条都让我们误判过。

## 10.1 最终结论

| 环节 | 结论 | 怎么确认的 |
|---|---|---|
| FPGA（PWM 输出）| ✅ 好的 | 测试固件里 LED 跟着相位闪 = 内部信号在动 |
| 电机（MG310）| ✅ 好的 | **直接用 FPGA 的 5V 接红黑两根线，转了** |
| 驱动板供电（Vin→3V3）| ✅ 好的 | 板子自带的电源指示灯亮 |
| **TB6612 输出级** | ❌ **烧了** | 两个通道都不输出、换电机也不转、但有电、信号也到了 |

**根因**：12V 电池 + 94% 占空比驱动 7.4V 电机，中途还有堵转；再加上下面 10.2 的"STBY 倒灌"让板子过热。**一次过热把双 H 桥烧了。**

## 10.2 ★★★ 反直觉坑一：`STBY` 内部上拉到板载 3V3，从 FPGA 驱动它 = 倒灌

这块驱动板的 `STBY` **内部有上拉电阻到它自己的 3V3**。所以：

```
FPGA 的 3.3V ──► STBY ──(板上拉)──► 板子的 3V3 轨
                                      ↑
                        = 把 FPGA 的 3.3V 和板子的 3.3V 并联
                        → 两个稳压器互相倒灌 → 大电流 → 发烫
```

**症状**：板子烫到手感疼痛、但电机不转。

**正确做法**：`STBY` **悬空**，让板子自己的上拉把它拉高。

**教训**：遇到"驱动板有使能脚"时，先搞清楚它是**输入**还是**内部已上拉到自己的电源**。
不确定就**悬空测一次**，如果电机能转就说明它自带使能。

## 10.3 ★★★ 反直觉坑二："探针"会被寄生供电骗

我们用 FPGA 的一个输入脚 + LED 当"电压探针"去量板子的 3V3。结果：**板子根本没供电，探针也亮。**

原因：芯片未通电时，任何**输入脚被外部驱动为高**，电流会经输入端的 **ESD 保护二极管**倒灌到 VCC 轨：

```
FPGA 输出 3.3V ──► 板子的 AIN1 引脚 ──► ESD 二极管 ──► 板子的 3V3 轨
                                                        （约 2.7V，掉一个二极管压降）
```

2.7V 对 CMOS 输入照样算高电平 → LED 亮 → **假的有电**。

**教训**：
- 用 GPIO 当"电压探针"时，**被测板上不能有别的信号线连着**，否则读到的是倒灌电压。
- 判断"有没有电"最可靠的还是**板子自带的电源指示灯**，或者真正的万用表。

## 10.4 ★★ 反直觉坑三：`Vin−` 和 `Vout+` 是两个完全不同的焊盘

驱动板顶部是 **`Vin+` / `−`（电源输入）**，底部是 **`5V/3V3/Vout+`（稳压器输出）**。

往 `Vout+` 上接地 = **把稳压器输出短路到地** → 共用一个 USB 5V 源时，把 FPGA 的 5V 轨拉垮 → **FPGA 重启**。

⚠️ 这种接法还可能**永久损坏板子的稳压器**（电流倒灌进它的输出端）。
**接之前一定确认是顶部那两个大焊盘。**

## 10.5 有效的排查顺序（这次绕了十几圈才悟出来）

```
第 1 步：把系统切成最少的段
         不要一次接全部 —— 每步只留"必要的那几根"

第 2 步：先验供电，再验信号，最后验负载
         供电：板子的电源灯亮不亮（不是 GPIO 探针！）
         信号：测试固件让 LED 跟着输出闪（证明内部在动）
         负载：把负载直接接到一个已知电源上，看它动不动

第 3 步：怀疑"线"时，用**信号本身**去验证
         例：让 FPGA 输出恒定高，把探针挪到那根线的**远端**，
             亮 = 线通，灭 = 线断。比万用表便宜，但要小心 10.3 的倒灌
```

**这次最关键的一步**：把电机从"FPGA→驱动板→电机"三段链路里**摘出来**，
只用 2 根线接 FPGA 的 5V —— 电机一转，立刻把范围锁死到驱动板。

## 10.6 台架测试的三条铁律（这次全违反了）

| 铁律 | 违反的后果 |
|---|---|
| **堵转保护不能关** | 我为让电机转把 `GUARD_ENABLE` 设 0，等于拆了保险 → 堵转时无任何保护 |
| **占空比要从低往上试** | 一上来 94%，12V 直逼 7.4V 电机 |
| **第一次带载前必须空载、悬空轮子** | —— |

**正确做法**：`GUARD_ENABLE=1` + **低占空比（20~30/128）** 起步，
电机转起来了再逐步加。**不能为了"让它动"去拆保护。**
