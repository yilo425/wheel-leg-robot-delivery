**轮编号约定**（★ 全项目统一，机械组按这个接线）：

| 索引 | 位置 | 左/右 | `STEER_COEF` |
|---|---|---|---|
| 0 | 左前 FL | 左 | **+1** |
| 1 | 右前 FR | 右 | **−1** |
| 2 | 左后 RL | 左 | **+1** |
| 3 | 右后 RR | 右 | **−1** |

> **按位置编号**（FL/FR/RL/RR），不是按左右分组。
> 系数和 = 0，所以转向不会附带整体加减速。
>
> ⚠️ **这里曾经出过一个真 bug**：`motion_decision.v` 原来按「0,1=左；2,3=右」
> （按侧面分组），而引脚表按「0=左前 1=右前 2=左后 3=右后」（按位置分组）。
> 两边各自自洽，**合起来就是错的** —— 机械组按位置接好线，转向会整个反过来。
> 2026-10-13 统一成**按位置**（也是 4 轮机器人的通用约定）。

> ⚠️ **这个编号必须由机械组确认**（见 §4）。装反了会导致转向反向。

## 2. ARM ↔ FPGA 通信接口（UART）

> 完整的协议原文见 `uart_frame_protocol.md`。这里是**够用版**。

### 2.1 物理层

| 项 | 值 |
|---|---|
| 接口 | UART（异步串口） |
| 波特率 | **115200** |
| 数据位 / 校验 / 停止位 | **8N1**（8 数据位，无校验，1 停止位） |
| 电平 | **3.3V TTL** |
| 流控 | 无 |
| 地线 | **必须共地** |

> **电平警告**：树莓派 / K230 / Luckfox 的 GPIO UART 都是 3.3V，**可以直接接 FPGA**。
> 如果用了 5V 逻辑的 USB-TTL 模块调试，**必须加电平转换**，否则会打死 FPGA 引脚。

### 2.2 帧格式

```
+--------+--------+--------+--------+--------+---------+--------+
| 帧头   | 版本   | 帧类型 | 长度   | 数据   | 校验    | 帧尾   |
| 0xAA55 | 0x01   | 1B     | 2B大端 | N 字节 | BCC 1B  | 0x55AA |
+--------+--------+--------+--------+--------+---------+--------+
                     └──────── BCC 计算范围 ────────┘
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2B | 固定 `AA 55` |
| 版本 | 1B | 当前 `0x01` |
| 帧类型 | 1B | 见 §2.3 |
| 长度 | 2B | **数据段**字节数，**大端**（高字节在前） |
| 数据 | NB | 载荷 |
| 校验 | 1B | **BCC = 版本 ^ 类型 ^ 长度高 ^ 长度低 ^ 所有数据字节**<br>**不含帧头帧尾** |
| 帧尾 | 2B | 固定 `55 AA` |

**帧总长 = 9 + N 字节。**

> **易错点**：帧开销是 **9 字节**（2 头 + 1 版本 + 1 类型 + 2 长度 + 1 校验 + 2 尾），
> 不是 10。我们在自测时就把这个算错过。

### 2.3 帧类型表

| 值 | 名称 | 方向 | 载荷长度 | 说明 |
|---|---|---|---|---|
| `0x01` | `IMAGE_DATA` | FPGA→ARM | 变长 | **预留**，本方案基本不用 |
| `0x02` | **`VISION_RESULT`** | **ARM→FPGA** | 1+7n | **★ B 主要要发的** |
| `0x03` | `ACK` | 双向 | 1 | 确认收到 |
| `0x04` | `CONFIG` | 双向 | 变长 | 参数配置 |
| `0x10` | **`TELEMETRY`** | **FPGA→ARM** | **13** | **★ FPGA 回传状态**<br>（状态1 + 速度2×2 + 距离2 + 姿态2×3） |

**未知类型的处理**：FPGA 侧收到未知类型会**按长度收完但仍丢弃**（保持帧同步不丢）。
所以 ARM 侧发错类型**不会导致通信死掉**，只会被忽略。

### 2.4 载荷格式

#### `0x02 VISION_RESULT`（ARM → FPGA）★ 主要接口

```
+--------+--------+--------+--------+--------+--------+
| 目标数 | 序号   | 类别   | x 中心 | y 中心 | 置信度 |
| 1B     | 1B     | 1B     | 2B     | 2B     | 1B     |
+--------+--------+--------+--------+--------+--------+
   每个目标 7 字节，重复「目标数」次
```

| 字段 | 范围 | 说明 |
|---|---|---|
| 目标数 | 0..8 | **0 表示本帧无目标**（合法，不是错误） |
| 序号 | 0..7 | 目标索引 |
| 类别 | 见下 | 目标类别编码 |
| x 中心 | 0..65535 | **归一化**到 0..65535（与分辨率解耦） |
| y 中心 | 0..65535 | 同上 |
| 置信度 | 0..100 | 百分比 |

**类别编码 → FPGA 动作**：

| 值 | 含义 | FPGA 侧动作 |
|---|---|---|
| `0x00` | 无 | — |
| `0x01` | 人员 | 减速 + 保持距离 |
| `0x02` | 障碍物 | 绕行 |
| `0x03` | 目标点/终点 | 向目标点行进 |
| `0x04` | **低矮障碍** | **触发升降腿越障**（`VIS_LOW_OBST` 参数） |

**归一化坐标的换算**（ARM 侧）：

```python
cx_norm = int(cx_pixel / image_width  * 65535)

```

**FPGA 侧的判决门限**（也已写进协议，ARM 不用管，但知道有好处）：

| x 中心范围 | 判定 |
|---|---|
| `< 21845`（左 1/3） | 目标偏左 |
| `21845 .. 43690`（中 1/3） | 正前方 |
| `> 43690`（右 1/3） | 目标偏右 |

#### `0x10 TELEMETRY`（FPGA → ARM，建议 10Hz）

+--------+--------+--------+--------+--------+--------+--------+

### 2.5 FPGA 侧的健壮性设计（ARM 侧需要知道的）

这些是 **FPGA 已经实现并验证过**的行为，ARM 侧可以依赖：

| 行为 | 说明 |
|---|---|
| **帧内超时保护** | 任何中间状态超过 `FRAME_TIMEOUT`（默认 20ms）没收到下一字节 → **回帧头搜索状态并报 `rx_timeout`**。<br>**所以 ARM 发一半断掉，FPGA 不会永久卡死。** |
| **BCC 错不交付** | 校验失败 → 报 `rx_bcc_err`，**帧被丢弃**，同步自动恢复 |
| **未知类型不丢同步** | 未知类型 → 按长度收完 → 丢弃 → **下一帧照常接收** |
| **前导噪声免疫** | 帧前有任意垃圾字节（包括连续的 `AA`）**都能正确同步** |
| **长度超上限丢弃** | `N > 64` → 整帧丢弃，**缓冲区不会溢出** |

**实测验证**：`tb_uart_frame` **58 项检查全通过**，覆盖了以上全部异常场景。

> 其中最有价值的一条：**故意改坏 BCC 后，紧接着发一帧正常的，FPGA 能立刻收到** ——
> 说明同步不会因为一次错误而丢失。

### 2.6 Python 参考实现

```python
import struct

HDR  = b'\xAA\x55'
TAIL = b'\x55\xAA'
VER  = 0x01

def bcc(data: bytes) -> int:
    """校验范围：版本 + 类型 + 长度(2B) + 数据"""
    x = 0
    for b in data:
        x ^= b
    return x

def pack_frame(ftype: int, payload: bytes) -> bytes:
    body = struct.pack('>BBH', VER, ftype, len(payload)) + payload
    return HDR + body + bytes([bcc(body)]) + TAIL

def vision_result(targets):
    """targets: [(类别, cx_norm, cy_norm, 置信度), ...]"""
    p = bytes([len(targets)])
    for idx, (cls, cx, cy, conf) in enumerate(targets):
        p += struct.pack('>BBHHB', idx, cls, cx, cy, conf)
    return pack_frame(0x02, p)

# 例：1 个目标，类别=人员，中心(0.30, 0.50)，置信度 88%
frame = vision_result([(0x01, int(0.30*65535), int(0.50*65535), 88)])
print(frame.hex(' '))
```

**解析 FPGA 回传**：

```python
def parse_frames(buf: bytearray):
    """从缓冲区里尽量多地解析出完整帧，返回 (帧列表, 剩余缓冲)"""
    frames = []
    while True:
        i = buf.find(HDR)
        if i < 0:
            del buf[:-1]          # 只保留最后一个字节（可能是 0xAA）
            break
        if i > 0:
            del buf[:i]           # 丢掉帧头之前的垃圾
        if len(buf) < 6:
            break
        ver, ftype, n = struct.unpack_from('>BBH', buf, 2)
        total = 9 + n
        if len(buf) < total:
            break
        body = bytes(buf[2:6+n])
        if bcc(body) != buf[6+n] or bytes(buf[total-2:total]) != TAIL:
            del buf[:2]           # 这帧坏了，跳过这个帧头继续找
            continue
        frames.append((ftype, bytes(buf[6:6+n])))
        del buf[:total]
    return frames, buf
```

## 3. ARM 侧要和 FPGA 对齐的 5 个约定

| # | 约定 | 说明 | 谁拍板 |
|---|---|---|---|
| 1 | **类别编码** | 只能用 §2.4 表里的 `0x00`~`0x04`，扩展要先商量 | B ↔ A |
| 2 | **归一化坐标** | 一律 0..65535，**不要发像素坐标** | B |
| 3 | **发送频率** | 建议 **10Hz**（100ms 一帧）。太快 FPGA 处理不过来，太慢避障反应迟钝 | B ↔ A |
| 4 | **视觉失效时的行为** | FPGA 侧**不依赖** ARM：`vision_valid=0` 时 **按"无障碍但限速"处理**，不会停车也不会飞车 | A（已实现） |
| 5 | **手动遥控通道** | `manual_sel` 已预留（`top.v` 第 216 行），需要时通过 `CONFIG` 帧下发 | 待定 |

> **第 4 条特别重要**：ARM 死机/断线时，机器人**会继续以限速直行**，而不是失控。
> 这是刻意的设计 —— **安全逻辑不能依赖上层是否正确**。

| 8 | **电机驱动板型号** | 决定 PWM 频率、死区、使能极性 | `pwm_motor.STEP_DIV` / `ZERO_DEADBAND` | |
| 9 | **驱动板逻辑电平**（3.3V / 5V） | 5V 必须加电平转换 | 硬件接线 | |
| 10 | **★ `lift_done` 从哪来** | 是舵机位置反馈？限位开关？还是固定延时？<br>**三者的 RTL 实现完全不同** | `main_fsm` 的越障阶段 | |
| 11 | **舵机型号与控制方式** | PWM 频率、脉宽范围 | `servo_lift` | |
| 12 | **硬件急停方案** | 现在是软件急停（按键）。<br>**是否需要一路直接切断电机电源的硬件回路？** | 安全设计 | |
| 13 | **FPGA 引脚分配表** | `top.cst` 里全是 `PIN_xx` 占位值 | **上板** | |

### 4.1 第 10 项为什么最关键

`main_fsm` 的越障流程是：

```
抬腿 (lift_cmd=1) → 等 lift_done → 前进 → 放腿 (lift_cmd=0) → 等 lift_done → 完成
```

**`lift_done` 的来源决定了整个阶段的设计：**

| 如果来自… | RTL 要怎么做 |
|---|---|
| **限位开关** | 边沿检测 + 消抖（复用 `encoder_decode` 的滤波思路） |
| **舵机位置反馈**（电位器/PWM 回读） | 需要 ADC 或脉宽测量，**工作量大** |
| **固定延时** | 最简单，但**不可靠**（堵转时不知道） |

**现在 `main_fsm` 里已经用超时兜底**（`LIFT_TIMEOUT_MS = 3000`），
即使 `lift_done` 永远不来，也会在 3 秒后放弃并报 `error_flag` —— **不会卡死**。

## 6. 上电时序与安全逻辑

### 6.1 上电顺序（建议）

```
1. 只给 FPGA 供电，烧 LED 流水灯 → 确认板子活着、时钟在跑
2. 接编码器，手动转轮子 → 看 LED 或 state_dbg 有无变化
3. 接驱动板 + 电机（★ 先架空轮子，不要落地）
4. 接按键，测急停：按 key[1] → motor_enable 应立刻变 0 且 state 进 S_ESTOP
5. 接 TOF → 看 dist_mm 数值是否合理
6. 接 ARM（uart_tx/rx/GND）→ 跑通信联调
7. ★ 全部正常后才落地跑
```

### 6.2 LED 含义（现场调试用）

| LED | 亮表示 |
|---|---|
| `led[0]` | **复位已释放，板子活着**（最基本的心跳） |
| `led[1]` | **电机使能中** |
| `led[2]` | 正在**避障或越障** |
| `led[3]` | **曾经进入过安全停车**（锁存，需复位清除） |

### 6.3 安全逻辑（已实现，答辩素材）

| 机制 | 行为 | 为什么这样设计 |
|---|---|---|
| **急停** | `key[1]` 按下 → **组合逻辑直接断 `motor_enable`，0 拍生效** | 安全不能等状态机 |
| **急停不误报故障** | 人工急停**不**置 `error_flag`，只有超时/舵机故障才置 | 区分"人按的"和"真故障" |
| **所有等待都有超时** | 避障 5000ms / 越障 3000ms / 过障 2000ms | **没有超时就会永久卡死** |
| **视觉失效不停车** | `vision_valid=0` → 按"无障碍但限速"处理 | ARM 死机不应导致机器人停摆 |
| **传感器故障 = 限速** | TOF 报错 → 限速，不是急停 | 单个传感器坏不应让任务失败 |
| **关使能强制归零** | `enabled=0` → 内部占空比强制 0，**不依赖上层是否记得清零** | 防御性设计 |

**急停路径（0 拍生效）** —— 逻辑分两处，**不要写重**：

```verilog
// ① top.v 第 215 行：按键 -> estop 电平
wire estop_sig = ESTOP_FROM_KEY ? ~key[1] : 1'b0;   // key[1] 低有效

// ② main_fsm.v 第 395 行：estop 直接组合进 motor_enable
assign motor_enable = motor_en_r & ~estop;          // ★ 纯组合，0 拍

// ③ top.v 第 343 行：顶层直接引出，**故意不再与一次 estop**
assign m_en = motor_enable_fsm;
```

> **为什么顶层不再与一次**（`top.v` 第 339-341 行有注释说明）：
> `main_fsm` 内部已经把 estop 组合进去了，顶层再做一次是**重复逻辑**，
> 而且会让"到底是谁断的使能"变得难查。
>
> **调试提示**：如果板上没焊 `key[1]`，读到的电平不确定，会看起来像"按了急停、
> 什么都没反应"。这时把 `top.v` 的 `ESTOP_FROM_KEY` 参数置 0 即可绕过。

> 波形实测可以证明：`estop` 和 `motor_enable` **在同一时刻跳变**，状态机晚 1 拍才进 `S_ESTOP`。
> **这是答辩时最值得展示的一张波形图。**

### 6.4 Linux SBC 的启动时间问题

如果用**树莓派 / K230 / Luckfox** 做视觉，**开机要 20~30 秒**。

**结论**：
- **FPGA 不应该等 ARM** —— 上电后 FPGA 独立运行
- 建议**默认进 `S_MANUAL`**，收到第一帧 `VISION_RESULT` 后才允许进 `S_AUTO`
- 这样即使 ARM 还没起来，机器人也是可控的

### 1.5 视觉类别表（FPGA 侧实现状态）

ARM 发 `VISION_RESULT(0x02)`，载荷里每个目标带一个**类别码**。
`main_fsm` 按这张表动作：

| 类别 | 名称 | FPGA 行为 | 实现位置 |
|---|---|---|---|
| `0x00` | 无 | 不动作（空目标帧也走这条） | — |
| `0x01` | 人员 | 不改状态；靠 `steer` 与限速 | 未实现 |
| `0x02` | 障碍物 | **进 AVOID（限速绕行）** | `VIS_OBST` |
| `0x03` | 目标点 | 不改状态；靠 `steer` 趋向 | 未实现 |
| `0x04` | 低矮障碍 | 进 LIFT（抬腿跨越） | `VIS_LOW_OBST` |

⚠️ **曾经的问题**：只实现了 `0x04`。而 ARM 侧 `camera_vision.py`
固定发 `0x02` —— 两边对不上，结果是"车看到障碍物不躲"。
现在 `0x02` 已实现。

⚠️ **`VIS_HOLD_MS`（默认 300ms）**：ARM 是 10Hz 发的，
`vision_valid` 是**单拍脉冲**。如果不加保持窗口，AVOID 只会持续
1 拍就退出，等于没避障。这个值必须 **大于帧间隔**（1000/TARGET_HZ），
否则每帧之间会解除一次。
