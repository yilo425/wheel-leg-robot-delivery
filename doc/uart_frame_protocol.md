# FPGA ↔ ARM 通信帧协议

> 用途：摄像头视觉结果（ARM → FPGA）与调试/状态回传（FPGA → ARM）
> 物理层：UART，115200 8N1，3.3V TTL，**必须共地**
> 版本：v1.0

---

## 1. 帧结构

```
+--------+--------+--------+--------+--------+---------+--------+--------+
| 帧头   | 版本   | 帧类型 | 长度   | 数据   | 校验    | 帧尾   |        |
| 2B     | 1B     | 1B     | 2B     | NB     | 1B      | 2B     |        |
| 0xAA55 | 0x01   | 见下表 | N      | N 字节 | BCC     | 0x55AA |        |
+--------+--------+--------+--------+--------+---------+--------+--------+
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2B | 固定 `0xAA 0x55`（高字节在前） |
| 版本 | 1B | 协议版本，当前 `0x01` |
| 帧类型 | 1B | 见 §2 |
| 长度 | 2B | **数据段**字节数 N（不含头/尾/校验），大端 |
| 数据 | NB | 载荷 |
| 校验 | 1B | BCC：从版本到数据最后一个字节的逐字节异或 |
| 帧尾 | 2B | 固定 `0x55 0xAA` |

### 字节序
- 多字节字段一律**大端**（高字节在前），与网络序一致，ARM 侧 Python 用 `struct.pack('>H', n)`。
- 图像/二进制载荷本身是字节流，不涉及字节序。

### 校验算法（BCC）

```c
uint8_t bcc(const uint8_t *buf, int n) {   // buf 从"版本"字节开始
    uint8_t x = 0;
    for (int i = 0; i < n; i++) x ^= buf[i];
    return x;
}
```

```python
def bcc(payload_after_header: bytes) -> int:
    x = 0
    for b in payload_after_header:
        x ^= b
    return x
```

> 校验范围是 **版本 + 帧类型 + 长度 + 数据**，不含帧头帧尾。
> 选 BCC 而不是 CRC16 的原因：FPGA 侧实现只要一个异或，时序压力为零；
> UART 本身有起始/停止位同步，短帧出错率很低。若后期发现误帧率高，
> 再升级 CRC16-CCITT，并同时升版本号到 0x02。

## 2. 帧类型定义

| 值 | 名称 | 方向 | 载荷 | 说明 |
|---|---|---|---|---|
| 0x01 | `IMAGE_DATA` | FPGA → ARM | 见 §3 | 图像行/块数据（预留） |
| 0x02 | `VISION_RESULT` | ARM → FPGA | 见 §3 | 目标检测结果 |
| 0x03 | `ACK` | 双向 | 1B 被确认的帧类型 | 确认收到 |
| 0x04 | `CONFIG` | 双向 | 见 §3 | 参数配置 |
| 0x10 | `TELEMETRY` | FPGA → ARM | 见 §3 | 状态回传（调试用） |

> 0x01 图像数据帧在本方案里基本不会用到：图像处理放在 ARM 侧本地完成，
> 不需要把整帧图像送进 FPGA。保留该类型是为了兼容"FPGA 侧做图像预处理"
> 的后备路线（例如 FPGA 先做灰度/二值化再送 ARM）。

## 3. 载荷格式

### 3.1 `0x02 VISION_RESULT`（ARM → FPGA）

```
+--------+--------+--------+--------+--------+--------+
| 目标数 | 序号   | 类别   | x 中心 | y 中心 | 置信度 |
| 1B     | 1B     | 1B     | 2B     | 2B     | 1B     |
+--------+--------+--------+--------+--------+--------+
   每个目标 7 字节，重复 "目标数" 次
```

| 字段 | 范围 | 说明 |
|---|---|---|
| 目标数 | 0..8 | 0 表示本帧无目标 |
| 序号 | 0..7 | 目标索引 |
| 类别 | 见下表 | 目标类别编码 |
| x 中心 | 0..65535 | 目标框中心 x，归一化到 0..65535（与分辨率解耦） |
| y 中心 | 0..65535 | 目标框中心 y |
| 置信度 | 0..100 | 百分比，0..100 |

类别编码（**以 RTL 为准**，2026-10-18 核实过 `rtl/app/main_fsm.v`）：

| 值 | 含义 | FPGA 侧实际动作 | RTL 里有专门的参数吗 |
|---|---|---|---|
| 0x00 | 无 | 不触发状态切换 | — |
| 0x01 | 人员 | ⚠️ **未单独实现**：只会走 `steer` 偏转，不减速 | ❌ |
| 0x02 | 障碍物 | **进 AVOID**（带保持窗口）| ✅ `VIS_OBST` |
| 0x03 | 目标点 | ⚠️ **没有专门的 GOAL 状态**：只靠 `steer` 让车朝它偏转，状态机仍是 AUTO | ❌ |
| 0x04 | 低矮障碍 | **进 LIFT 模式 0**（四腿一起抬）| ✅ `VIS_LOW_OBST` |
| 0x05 | 台阶/门槛 | **进 LIFT 模式 1**（两腿分段抬）| ✅ `VIS_STEP` |

> ⚠️ **两条以前写错、现已更正**（2026-10-18，ARM 侧同学核对 RTL 时发现）：
>
> 1. 旧文档把 `0x03` 写成"向目标点行进"，看起来像有 GOAL 导航 ——
>    实际 `main_fsm` 里**没有 `VIS_GOAL`**，`S_GOAL` 只由
>    `goal_reached` 引脚（`E16`，低有效）触发，语义是"**到达终点停车**"，
>    和"朝目标开过去"是相反的。所以 0x03 的实际效果只是
>    **通过 `steer` 偏转方向**，FPGA 不会进任何新状态。
> 2. `0x05` 台阶 RTL 一直有实现，但旧文档的类别表漏了它。
>
> **`0x01 人员` 也只是一个类别码**：RTL 没有"减速+保持距离"的逻辑，
> 它同样只通过 `steer` 偏转。要真做人员避让得另外加。

> **归一化坐标的意义**：ARM 侧换摄像头分辨率时，FPGA 侧代码不用改。
> FPGA 只需要 `x 中心 < 21845` 判左、`> 43690` 判右、中间判直行。

### 3.2 `0x04 CONFIG`（双向）

```
+--------+--------+--------+--------+
| 参数ID | 长度   | 值 ...          |
| 1B     | 1B     | 长度 字节       |
+--------+--------+--------+--------+
```

**一帧只放一个参数**：`LEN` 必须等于 `2 + 值长度`，否则整帧判非法（`cfg_bad`），
**对应寄存器保持原值不变**。多字节值一律**大端**。

| 参数 ID | 含义 | 长度 | 单位 | 范围（超界自动钳位）|
|---|---|---|---|---|
| 0x01 | 最大速度 | 2B | 编码器计数/窗口 | 1 .. 200 |
| 0x02 | 避障停车距离 | 2B | mm | 50 .. 2000 |
| 0x03 | 测速窗口 | 2B | ms | **暂未实现**（`encoder_decode` 的编译期参数），收到只计数忽略 |
| 0x04 | 避障减速距离 | 2B | mm | 50 .. 3000，且强制 `> 停车距离`（否则自动设为 `停车距离 + 50`）|
| 0x10 | 升降腿抬升高度 | 1B | 0..100 | 0 .. 100 |
| 0x11 | 升降腿动作超时 | 2B | ms | 500 .. 30000 |
| 0x20 | 手动模式开关 | 1B | 0/1 | 只接受 0 或 1，其它值判非法 |

> **钳位为什么算"成功"而不是"拒绝"**：配置写得离谱时（比如停车距离写成 0mm），
> 如果直接拒绝，上位机并不知道自己写错了；钳到安全边界并计 `cfg_valid` 更实用。
> 需要严格校验的场合请在上位机侧自己做。
>
> 未知 ID 一律**忽略**（计 `cfg_ign_cnt`），不算错 —— 这样协议可以向后兼容地扩展。

> ⚠️ **当前实现进度**（2026-10-18 更新，除 `0x03` 外**全部已生效**）：
>
> | ID | 解析 | 是否真正生效 |
> |---|---|---|
> | `0x01` 最大速度 | ✅ | ✅ 接进 `motion_decision.vref` |
> | `0x02` 停车距离 | ✅ | ✅ 接进 `main_fsm.dist_stop_mm` |
> | `0x03` 测速窗口 | 只计数 | ❌ `encoder_decode` 的编译期参数，窗口长度与计数器位宽耦合，暂不做 |
> | `0x04` 减速距离 | ✅ | ✅ 接进 `main_fsm.dist_slow_mm` |
> | `0x10` 抬腿高度 | ✅ | ✅ **接进 `servo_lift.lift_height`**（0..100 线性映射脉宽，100 = 旧行为）|
> | `0x11` 抬腿超时 | ✅ | ✅ **接进 `main_fsm.lift_timeout_ms`**（`t_up` 改成数毫秒）|
> | `0x20` 手动模式 | ✅ | ✅ 接进 `main_fsm.manual_sel` |
>
> **两个"改运行时"的实现细节**（都是为了不引入乘法器/除法器）：
> - `0x10`：`(PWM_MAX_US-PWM_MIN_US)*CYC_PER_US/100` 是**编译期常数**
>   （50MHz 下 = 1us = 50 拍/单位），运行时只做一次常数乘。
> - `0x11`：把 `t_up` 从"数时钟拍"改成**数毫秒**（加一个 1ms 节拍），
>   于是比较的是毫秒值，**省掉 16x16 乘法器**。代价：分辨率 20ns -> 1ms（等舵机完全够）。
>
> 覆盖情况：`tb_servo_lift` 场景 8（5 项）验 0x10，`tb_main_fsm` 场景 12（7 项）验 0x11。

### 3.2b `0x05 RC_CMD`（ARM → FPGA，手动遥控）

2026-10-28 新增。K230 收到手机网页摇杆后转成这个帧发给 FPGA。
**载荷固定 3 字节**，长度不对整帧丢弃（`rc_bad` 脉冲）。

| 偏移 | 字段 | 类型 | 范围 | 含义 |
|---|---|---|---|---|
| 0 | `steer` | int8 | −100..+100 | 转向，**正 = 右转**（和 `motion_decision.steer` 同号）|
| 1 | `speed` | uint8 | 0..100 | 速度百分比 |
| 2 | `seq` | uint8 | 0..255 | 发送端自增，用于丢帧统计 |

**speed → speed_scale 的映射**（FPGA 侧 `rc_rx.v`）：

| speed | speed_scale | 效果 |
|---|---|---|
| 0 | 0 | 停 |
| 1..50 | 1 | 慢 |
| 51..100 | 2 | 满 |

**★ 安全：500ms 看门狗**

`rc_rx.v` 里有一个毫秒计数器：收到合法帧就清零，否则累加。
超过 `TIMEOUT_MS = 500` 后 `rc_active` 立刻归 0，上层据此停车。
**复位后也必须是 0**（没收到过指令不使能），否则一上电就冲。

**`steer` 为什么要 ×16**

`motion_decision` 的转向项是 `steer >>> 4`。视觉那条路的 steer 量级是几十~几百，
遥控这边是百分比，直接送进去只有 ±6，几乎直线。所以 `rc_rx` 里把 steer 左移 4 位，
让 ±100 对应转向项 ±100（满速打满 = 一侧 0、另一侧限幅，原地转）。

### 3.3 `0x10 TELEMETRY`（FPGA → ARM，10Hz）

```
+--------+--------+--------+--------+--------+--------+--------+
| 状态   | 速度L  | 速度R  | 距离   | roll   | pitch  | yaw    |
| 1B     | 2B     | 2B     | 2B     | 2B     | 2B     | 2B     |
+--------+--------+--------+--------+--------+--------+--------+
```

| 字段 | 说明 |
|---|---|
| 状态 | 主状态机状态编码（见 `interface_spec.md` §3.4）—— **只占低 3 位** |
| 速度L/R | 左/右轮 `speed_cnt`，**有符号**，补码大端 |
| 距离 | TOF 距离，mm |
| roll/pitch/yaw | 姿态角，0.01 度/LSB，有符号补码 |

#### ★ 状态字节的高 4 位：标志位（2026-10-25 新增，**帧长不变，向后兼容**）

```
 bit7   bit6   bit5        bit4        bit3        bit2        bit1     bit0
 ┌─────┬─────┬───────────┬───────────┬────────────┬──────────┬────────┬────────┐
 │  0  │  0  │goal_reached│  spd_stale│  limited   │  error   │  state[2:0]     │
 └─────┴─────┴───────────┴───────────┴────────────┴──────────┴────────┴────────┘
```

| bit | 含义 | 用途 |
|---|---|---|
| 7,6 | 保留（恒 0）| — |
| 5 | `goal_reached` | 终点限位开关触发 |
| 4 | `spd_stale` | **测速反馈超时**（编码器断线）→ 已降级为开环，ARM 侧应报警 |
| 3 | `limited` | 至少一路占空比被限幅（爬坡/堵转前兆）|
| 2 | `error` | 故障标志（急停/堵转/状态机报错）|
| 1..0 | `state[2:0]` | 主状态（bit2 在上）|

> ⚠️ ARM 侧**只读低 3 位也能正常工作**（旧解析器不受影响）；
> 想用新标志时按位掩码读即可：`flags = (b0 >> 3) & 0x0F`，`state = b0 & 0x07`。

## 4. 收发状态机（FPGA 侧实现要点）

接收侧用字节流状态机，**绝不允许在 IDLE 之外丢弃字节后不同步复位**：

```
S_HDR1  : 等 0xAA
S_HDR2  : 等 0x55, 否则回 S_HDR1(若收到 0xAA 则停在本状态)
S_VER   : 收版本, 不匹配则回 S_HDR1
S_TYPE  : 收帧类型, 未知类型标记 "丢弃" 但仍按长度收完(保持同步)
S_LEN_H : 收长度高字节
S_LEN_L : 收长度低字节 -> 校验 N <= MAX_PAYLOAD(建议 64)
S_DATA  : 收 N 字节
S_BCC   : 收校验, 与累加值比对
S_TAIL1 : 等 0x55
S_TAIL2 : 等 0xAA -> 帧完成, 交给上层; 然后回 S_HDR1
```

**超时保护**：任何中间状态超过 `FRAME_TIMEOUT(建议 20ms @115200)` 未收到下一字节，
一律回 `S_HDR1` 并置 `frame_timeout` 标志。没有这个保护，一旦丢一个字节，
状态机可能永久卡在等长度/等校验上，现象是"通信莫名其妙死了"。

## 5. ARM 侧 Python 参考实现

```python
import struct

HDR = b'\xAA\x55'
TAIL = b'\x55\xAA'
VER = 0x01

def bcc(data: bytes) -> int:
    x = 0
    for b in data:
        x ^= b
    return x

def pack_frame(ftype: int, payload: bytes) -> bytes:
    body = struct.pack('>BBH', VER, ftype, len(payload)) + payload
    return HDR + body + bytes([bcc(body)]) + TAIL

def parse_frames(buf: bytearray):
    """从缓冲区里尽量多地解析出完整帧, 返回 (帧列表, 剩余缓冲)"""
    frames = []
    while True:
        i = buf.find(HDR)
        if i < 0:
            # 没有帧头, 只保留最后一个字节(可能是 0xAA)
            del buf[:-1]
            break
        if i > 0:
            del buf[:i]                    # 丢掉帧头之前的垃圾
        if len(buf) < 2 + 1 + 1 + 2:
            break                          # 头都还没收全
        ver, ftype, n = struct.unpack_from('>BBH', buf, 2)
        total = 2 + 1 + 1 + 2 + n + 1 + 2
        if len(buf) < total:
            break
        body = bytes(buf[2:2 + 1 + 1 + 2 + n])
        got_bcc = buf[2 + 1 + 1 + 2 + n]
        tail = bytes(buf[total - 2:total])
        if bcc(body) != got_bcc or tail != TAIL:
            del buf[:2]                    # 这帧坏了, 跳过这个帧头继续找
            continue
        frames.append((ftype, bytes(buf[2 + 1 + 1 + 2:2 + 1 + 1 + 2 + n])))
        del buf[:total]
    return frames, buf

# 组一个视觉结果帧: 1 个目标, 类别=人员, 中心 (0.3, 0.5), 置信度 88
def vision_result(targets):
    p = bytes([len(targets)])
    for idx, (cls, cx, cy, conf) in enumerate(targets):
        p += struct.pack('>BBHHB', idx, cls, cx, cy, conf)
    return pack_frame(0x02, p)

frame = vision_result([(0x01, int(0.30*65535), int(0.50*65535), 88)])
print(frame.hex(' '))
```
